## 备份内容与限制

| 项目 | 说明 |
|------|------|
| 包含 | **数据库（全部元数据）+ 安装配置**（`config.installed.json`） |
| 不包含 | **文件实体**（`storage/` 下的用户文件与 blob）。文件实体请通过存储卷快照 / 磁盘备份另行保障 |
| 完整性 | zip 包内附 `manifest.json` 与逐文件 **SHA-256**；坏包/被篡改包拒绝恢复（业务码 `3605`） |
| 密码安全 | 远端备份密码以 **Fernet 对称加密**存储（密钥由 `SECRET_KEY` 派生），接口永不回传明文，留空提交表示不修改 |

> 恢复只还元数据与配置：如果只恢复了备份而没有文件实体的备份，恢复后文件记录存在但物理文件缺失（下载会提示「物理文件已丢失」）。**数据库与存储卷必须配套备份**。

## 手动与定时备份

| 方式 | 操作 |
|------|------|
| 手动备份 | 「系统管理 → 备份恢复」点击**立即备份**；接口 `POST /api/admin/backup` 后台线程执行（同一时刻仅允许一个备份任务，重复触发返回 `3601`），前端进度轮询刷新列表 |
| 每日定时 | 系统设置开启 `backup_enabled` 并指定 `backup_hour`（0–23，默认 3）与 `backup_keep_count` |

**定时机制**：调度器**每小时 :17** 唤醒一次（cron minute=17），任务内自查「当前小时 == backup_hour 且开关开启」才执行；**修改小时/开关无需重启服务**。同秒多次备份文件名自动追加序号，避免唯一约束冲突。

## 备份目标配置

系统设置中二选一（`backup_target`）：

### 本地服务器

- 备份保存在服务器 `storage/backups/` 目录（随 `app-storage` 数据卷持久化）。

### 远端服务器

| 参数 | 设置键 | 说明 |
|------|--------|------|
| 协议 | `backup_protocol` | `sftp`（推荐，基于 paramiko，加密传输）/ `ftp`（兼容选项，**传输不加密**，仅限可信内网） |
| 服务器地址 | `backup_host` | IP 或域名；目标为 remote 时必填（`1223`） |
| 端口 | `backup_port` | SFTP 默认 **22**，FTP 默认 **21**（1–65535） |
| 用户名 | `backup_username` | — |
| 密码 | `backup_password` | Fernet 加密入库；界面永不回传明文；留空提交=不修改（匿名 FTP 允许空密码） |
| 远端目录 | `backup_remote_dir` | 默认 `/zhy-backups`；不存在时自动逐级创建 |

- 「**测试连接**」按钮（`POST /api/admin/backup/test-connection`）：验证连通性、登录与目录可写，**仅测试不保存**。
- 远端备份采用「**本地先打包 → 上传**」：上传失败自动**保留本地包**并在备份列表中标注失败原因。
- 设置保存为两阶段校验：全部字段通过才写入，避免半写入；只要请求涉及远端字段或目标为远端，就做远端完整性校验。

## 保留策略

- `backup_keep_count`（默认 7，范围 1–100）：每次备份成功后自动淘汰最旧的记录与文件（本地与远端同步清理）。
- 备份列表（`GET /api/admin/backups`）为**备份记录与存储端实际文件合并**的视图，并返回当前是否有任务在跑（`running`）。

## 备份包结构

```text
zhy-backup-<db_type>-<时间戳>.zip
├── manifest.json          # 版本、库类型、时间、逐文件 SHA-256
├── config.installed.json  # 安装配置（数据库连接串、密钥、存储目录、开关）
└── db.<ext>               # 数据库快照：SQLite 为 .db 文件；MySQL 为 dump SQL
```

文件名示例：`zhy-backup-mysql-20260919-031700.zip`。

## 恢复：四种方式与流程

「备份恢复」页提供四个入口（接口统一为 `POST /api/admin/backup/restore`）：

| 方式 | 参数 | 说明 |
|------|------|------|
| 服务器备份记录 | `backup_id` | 按备份记录 ID 恢复（远端记录由服务端先拉取） |
| 游离本地文件 | `remote_filename`（本地优先） | 恢复后旧备份记录随旧库消失，但文件可能仍在本地 `storage/backups/`；优先按文件名在本地查找，找不到再从远端下载 |
| 远端文件名 | `remote_filename` | 从远端 SFTP/FTP 按文件名下载后恢复 |
| 上传 zip 包 | multipart `file` | 在备份恢复页直接上传备份包恢复 |

### 强制流程

1. **风险确认**：必须带 `confirm=true`，否则返回 `3607`「恢复会覆盖当前数据库，请明确勾选确认后再执行」。
2. **包校验**：安全解压（防路径穿越）+ `manifest.json` 与 SHA-256 逐文件校验，坏包拒绝（`3605`）。
3. **pre-restore 快照**：恢复前自动把**当前数据库**留一份回滚快照到实例目录（`pre-restore-<时间戳>.db` / `.sql`）。
4. **执行恢复**：
   - SQLite：直接替换实例目录数据库文件；
   - MySQL/MariaDB：导入 dump 前统一释放 SQLAlchemy 连接池，避免本进程连接池持有**表元数据锁（MDL）**导致导入 worker 超时（v1.3.0 修复）；
   - 恢复后自动清理 Redis 中旧的设置/插件/JWT 吊销缓存，防止旧缓存覆盖回滚数据。
5. **恢复安装配置**：回写 `config.installed.json`。
6. **进程自动退出**：响应发出后 **2 秒**进程退出（`schedule_exit(2.0)`），由守护进程拉起：
   - Docker：内置 supervisor 自动拉起；
   - systemd / supervisor 部署：开箱即用；
   - **裸机前台 `python run.py`：需手动重启**。

## 数据库支持矩阵

| 数据库 | 备份 | 恢复 | 说明 |
|--------|------|------|------|
| SQLite | ✅ | ✅ | 快照为库文件直接打包 |
| MySQL / MariaDB | ✅ | ✅ | 自动适配 `mariadb-dump` / `mysqldump`（优先找 mariadb-dump）；Docker 内置 MariaDB 11 已验证 |
| PostgreSQL | ❌ | ❌ | 明确返回「暂不支持 PostgreSQL 数据库的备份恢复（v1.3.0 仅支持 SQLite/MySQL）」（业务码 `3606`），不会误操作 |

## 三数据卷备份建议

Docker 部署建议同时保障三个数据卷：

| 数据卷 | 内容 | 建议手段 |
|--------|------|----------|
| `app-mysql` | 数据库 | 应用内备份（本页功能）+ 卷快照/`mysqldump` 外部备份 |
| `app-storage` | 文件实体与本地备份包 | 磁盘级备份 / 快照（应用内备份**不含文件实体**） |
| `app-instance` | 安装配置 | 已包含在应用内备份包中；卷快照更稳 |

手工快照示例：

```bash
docker run --rm -v zhy-mysql:/data -v $(pwd):/backup alpine \
  tar czf /backup/zhy-mysql-$(date +%F).tgz -C /data .
docker run --rm -v zhy-storage:/data -v $(pwd):/backup alpine \
  tar czf /backup/zhy-storage-$(date +%F).tgz -C /data .
```

## 恢复演练与运维建议

- **定期演练**：备份的可用性只有恢复才能验证。建议季度性在测试环境用最新备份包走一遍「上传 zip 恢复」，确认 manifest/SHA-256 校验通过、服务自动拉起、设置与用户数据回滚正确。
- **pre-restore 快照的用途**：恢复前自动在实例目录生成 `pre-restore-<时间戳>.db`（SQLite）或 `pre-restore-<时间戳>.sql`（MySQL）。恢复结果不符合预期时，可用该快照手工回滚（SQLite 替换文件；MySQL 重新导入 SQL）后重启服务。
- **恢复期间的写入**：恢复会覆盖数据库，务必在低峰期执行，并提前告知用户暂停上传；恢复后 Redis 旧缓存已被自动清理，无需手工处理。
- **本地备份目录也在存储卷里**：`storage/backups/` 位于 `app-storage` 卷，即「本地备份」与文件实体同盘。若担心单点故障，请配置远端 SFTP/FTP 目标，或把本地备份再同步到异地。
- **多 worker 注意**：gunicorn 多进程部署下备份任务有「运行中」互斥（`3601`），任务本身幂等；恢复必须由单一进程完成（进程退出由守护拉起属于设计行为，不要在恢复中 kill -9）。

## 常见失败排查

| 现象 | 业务码 | 原因与处理 |
|------|--------|------------|
| 「已有备份任务正在执行」 | `3601` | 上一个备份未结束，稍后刷新列表再试 |
| 备份/测试连接失败提示连接类错误 | `3603` | 检查主机/端口/账号密码、防火墙；SFTP 需密码认证；FTP 不加密仅限可信内网 |
| 恢复时提示备份不存在 | `3604` | 记录 ID 错误或远端文件已被清理；改用「上传 zip」方式 |
| 「备份包校验失败/非法」 | `3605` | zip 损坏或被修改；manifest/SHA-256 校验不通过，换包 |
| 「暂不支持 PostgreSQL…」 | `3606` | 用 MySQL/MariaDB 或 SQLite 部署，或自行用 `pg_dump` 做外部备份 |
| 恢复按钮点击无确认生效 | `3607` | 必须勾选风险确认（`confirm=true`） |
| 恢复后服务没起来 | — | 检查是否裸机前台运行（无守护不自动拉起），手动重启即可 |
| 恢复后文件打不开 | — | 只恢复了元数据未恢复文件实体；用配套的 `app-storage` 快照还原 |
| 远端备份列表缺文件但本地有 | — | 上传失败时自动保留本地包并标注原因，可先下载本地包 |
